# UI/UX 调研与博采

目标是**受启发，不照抄**。别的产品（包括高斯）只是做出了还不错的东西，它们的做法要拆成"解决什么问题、靠什么机制、依赖什么前提"，再决定我们要不要、怎么改。

每次调研都交付两条线：

- **A 和谐加强**：不动骨架，在现有交互上加强。每一条改动都要能写成一条对所有步骤都成立的规矩，和已有规矩不冲突。
- **B 重构方向**：可以动骨架（布局、导航、讲述方式、结论区的形态）。必须说清它换来了什么是 A 做不到的，以及老课件怎么迁移。

和用户用中文交流。所有样张做在会话 scratchpad 的副本里，页内放切换按钮和原版对照；用户选定之前不改仓库里的 `mockups/` 和 `app/`。

## 第 0 步：把任务做深，不做大

开始调研前，先针对这次的具体题目写一段"深化说明"给用户看，回答四个问题，然后把用户的要求改写成一份准确的任务说明。不要跳过，也不要写成通用套话：每一条都要落到这次的题目上。

1. **顶尖的人会多做什么**：这个领域最好的设计研究员、学习体验设计师会做哪些用户没有提出的事？（例如：先审自己的产品、按教学时刻拆题、先定验收标准再出方案、考虑课堂投影场景、考虑写课的人能不能写出来。）
2. **从哪些最原始的材料入手**：他们看的是一手材料，不是别人整理好的结论。列出这次要用的原始材料，和准备不用或只当线索用的二手材料。
3. **具体用哪些方法和工具**：方法要有名字、有步骤，工具要能在本环境跑（见下文"工具"）。
4. **除了你和我，还有什么能证明结果是对的**：客观测量、盲评、学习科学的已有证据、学生和老师的真人测试、自动检查。写清哪些这次能做到，哪些做不到、要用户安排。

改写后的任务说明按这个格式：

```
题目：<一句话>
服务的教学时刻：<讲述 / 停点 / 反馈与提示 / 证据 / 结论沉淀 / 练习 / 小测与回看 / 导航，选相关的>
基线：<现在的样子，附截图路径和测量数字>
要回答的问题：<2–4 个，可证伪>
原始材料：<清单>
方法：<清单>
交付：A 线 n 条、B 线 1–2 个方向，每条附样张和测量对比
验收：<指标和阈值；盲评；需要用户安排的真人测试>
不做：<明确排除的范围>
```

用户确认或修改任务说明后再往下做。用户说"直接做"时，把任务说明写进第一份报告的开头，照常往下做。

## 第 1 步：先审自己

不先看清自己，借鉴就会变成换皮。

1. **教学时刻清单**：把一节课（默认第 4 节 `mockups/collision/`）每一步归到上面八种教学时刻里，数清每种时刻出现多少次、在哪几步。停点的密度是我们和多数产品最大的不同（第 4 节第 1–6 幕 15 步里有 14 个停点），任何方案都要在高密度停点下成立。
2. **截图**：每种时刻至少挑两步，截亮色、夜光，电脑 1280×800、手机 390×844。用 Playwright，`executablePath: '/opt/pw-browsers/chromium'`，不要运行 `playwright install`。
3. **测量基线**：用 `scripts/measure.mjs` 量每张截图对应的状态（用法见脚本开头注释），记下视线路程、关键块是否在首屏外、版面跳动、对比度不达标的文字数、点按目标过小数、首屏字数、字号种类数。
4. **列出已定的规矩**，方案不能悄悄违反；确实要改的，单独列出来请用户定：
   - 颜色只给物理量：蓝 = 速度，红 = 力和"不可能"，金 = 能量。状态色用墨色，不用彩色。
   - 调色板以 `app/src/theme.ts` 为准。
   - 动效：物体运动按物理算、不加缓动；修饰动效只用 `plans/direction.md` 第三节表里定过的。
   - 字体角色：正文 Noto Sans SC，物理符号 Source Serif 4 斜体，读数等宽。
   - 组件库只加不删（`CLAUDE.md`）：方案落到库里时，已有组件的新属性一律可选。
   - 课件是纯文本，由人或模型来写：写课的人写不出来的交互，不算可行方案。
5. 看 `plans/direction.md`、`plans/lesson-design-standard.md` 里和这次题目相关的段落。

## 第 2 步：原始材料

按可信度从高到低用：

1. **亲手用真实产品**：能在浏览器里打开的，用 Playwright 一步步走、逐帧截图，用 `measure.mjs` 量真实的尺寸、字号、间距、对比度。不凭截图目测比例。
2. **用户给的截图和录屏**：保存路径记进报告。只有截图时，量像素比例，并注明"由截图估算"。
3. **产品团队自己写的设计说明**：设计博客、更新日志、演讲（如 Duolingo、Brilliant 的博客）。它们讲的是"为什么这么做"，比外人的拆解可靠。
4. **用户原声**：应用商店评论、论坛里的抱怨。差评最能说明一个做法的代价。
5. **研究原文**：学习科学和人机交互的论文、专著。引用时写作者、年份、具体结论；只读到摘要的注明"未读原文"。
6. **规范原文**：WCAG 2.2、Apple HIG、Material 3。

**二手材料只当线索**：Refero、Mobbin 这类截图库是别人策展过的单张截图，看不到前后流程，只用来扩大视野、找该去亲手看的产品。设计博客的"十大技巧"、AI 生成的总结不作为依据。

来源清单和本环境实测的可达性见 `references/sources.md`。Refero 的工具名是 `mcp__refero__*`，要先用 ToolSearch 载入；提示未授权时告诉用户去 claude.ai 的连接器设置里授权，不要向用户要令牌。

**广度要求**：每个题目至少看 2 个教育产品、2 个非教育产品（找"问题同构"的：对话加画布、视频章节、滚动叙事、游戏教学关、阅读器），并找至少 1 条学习科学或人机交互的原理。一个做法只在一个产品里见到、又没有原理支撑时，只能算"孤例"，不能当规律用。

## 第 3 步：拆机制，不抄外观

每个值得借鉴的做法写一张"做法卡"：

```
### <做法名>
- 出处：<产品、页面或步骤；截图路径或链接；查看日期>
- 教学时刻：<它服务哪一种>
- 解决的问题：<学生或老师遇到的什么困难>
- 机制：<为什么有效；对应的原理，如 Mayer 的空间邻近、信号、分段、去冗余，认知负荷，预测—观察—解释，提取练习>
- 依赖的前提：<离开它就不成立的条件，例如"有配音才能自动连播""停点少才能整页出题">
- 在我们这里：<放到哪；和已定规矩冲突吗；要改哪些组件或属性；写课的人要多写什么>
- 可测的预期：<哪个指标往哪个方向变，大约多少>
- 什么时候会坏：<反例、边界情况，如长选项、手机、夜光、投影>
```

"依赖的前提"最容易漏，也最要紧。例：高斯的板面能那么干净，一部分原因是停点少、讲述有配音；我们停点多、没有配音，同样的版面直接搬过来，选项就没地方放。

## 第 4 步：出方案

**A 线（和谐加强）**

- 用现有令牌（颜色、字号、间距、圆角），不新造视觉语言。
- 每条改动写成一句规矩，例如"问题在哪问，就在哪答""板上只放画面、表格、演算"。
- 写完把新旧规矩放在一起检查：有没有两条互相打架？有没有哪种教学时刻被漏掉？
- 一般 3–7 条，每条单独可取舍。

**B 线（重构）**

- 一次只提 1–2 个方向，每个方向要有完整的一步走查：从进课到小测结果都走得通。
- 写清：换来了什么（对应哪些基线指标）；丢掉了什么；对组件库的影响（新组件、新写法）；老课件怎么迁移（能不能用 `genui patch` 或脚本批量迁）。
- 样张至少覆盖讲述、停点、练习三种时刻。

**样张**

- 复制 `mockups/` 里对应的课到 scratchpad，在副本上改。
- 页内放切换按钮（原版 / A / B），切换状态存在 localStorage，同一步能来回比。
- 发布成多文件 Artifact（`files` 列出 js、css），每次改完用同一路径重新发布。

## 第 5 步：验证（除了你和我，还有什么能证明它对）

每条结论标上证据等级：**已测量 / 已盲评 / 有原理支持 / 待真人测试**。

1. **客观测量**：用 `measure.mjs` 量改前改后同一状态，列对比表。默认阈值：
   - 停点时，题目到选项的视线路程尽量短，选项不能在首屏外；
   - 同一步内推进时，版面跳动为 0；
   - 正文对比度 ≥ 4.5，大字 ≥ 3（WCAG 2.2 AA）；有意做淡的已读讲述文字，单独列出并说明理由；
   - 点按目标：手机 ≥ 44×44，电脑 ≥ 24×24；
   - 首屏字数、字号种类数只做参考，看趋势，不设硬线。
2. **盲评**：开一个新的子代理，只给它几个方案的截图（随机编号，不说哪个是新的）和评价标准，不给我的结论，让它独立排序并说理由。它和我的判断不一致的地方，在报告里写出来。
3. **原理**：方案的预期和学习科学已有结论是否一致，引出处。
4. **真人测试**（要用户安排，报告里给现成的测试单，见 `references/user-test.md`）：5 名学生出声思考；1 名老师用投影试一节课。
5. **兼容和自动检查**：方案涉及组件库时，`cd app && npm run verify` 全部通过；老课件照常渲染。

## 第 6 步：交付

- 报告写成 HTML Artifact 发给用户，结构：
  1. 改写后的任务说明；
  2. 基线；
  3. 做法卡（按教学时刻分组）；
  4. A 线规矩表，每条附改前改后截图和数字；
  5. B 线方向；
  6. 证据等级汇总；
  7. 请用户定的问题。
- 聊天里只写结论和要用户定的事，不贴整份报告。
- 用户选定后再动仓库：改 `mockups/`，同步更新 `plans/direction.md` 或相关规格里的规矩，跑 `cd app && npm run verify`，提交推送到当前指定的分支。
- 用户否掉的方案，在报告里记下否决的理由，下次调研别再端出来。

## 不要做

- 不要只看截图就下结论，也不要凭印象说"更干净""更好用"，要给出量到的数或盲评结果。
- 不要整体换皮，也不要一次端出十几条灵感。
- 不要把一个产品的做法当规律，至少要在两个地方独立见到，或者有原理支撑。
- 不要脱离教学时刻谈界面，每条方案都要说清它服务哪一刻。
- 不要为了像某个产品去违反已定的规矩；确实要改规矩，单独请用户定。

## 工具

- `scripts/measure.mjs`：量页面某一状态的界面数据（视线路程、首屏外、版面跳动、对比度、点按目标、字数、字号种类），可以先设 localStorage、依次点击再量。对外部网站同样能用。
- Playwright：截图、逐步走流程。拼对比图用 Python PIL。
- Refero MCP：找参考截图和流程。
- WebSearch / WebFetch：读产品团队的设计说明、研究原文、规范原文。
- Agent：盲评子代理。
